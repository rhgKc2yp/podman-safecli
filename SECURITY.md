# Security and update policy

- **Isolation:** Rootless Podman, no host sockets/home mounts, capability drop and `no-new-privileges`. `usb` exposes one device; `nested` relaxes seccomp. Networking is enabled and may reach the LAN. A VM is safer for high-risk programs.
- **Base:** `docker.io/library/fedora:latest` (latest stable release); fresh uncached builds execute `dnf upgrade --refresh`, then use Fedora's own DNF security advisory query to reject builds with pending security updates or advisory-query errors. Fedora major upgrades can cause build failures. Watch the actual Fedora version, advisories and build logs.
- **Preinstalled toolchains:** All profiles include the core Node.js, Python, Rust and Go CLI toolchains plus basic compilers from Fedora repositories. This increases image size and attack surface compared with a minimal base. The shared package list is in `scripts/install-cli-toolchain.sh`; additions are subject to the same Trivy gate. No language-registry install scripts execute at build time.
- **Cadence:** The GHCR workflow runs approximately every three days, plus pushes and manual runs. GitHub cron uses days 1, 4, 7, ... of each month, not a guaranteed 72-hour cadence; scheduled jobs may be delayed or suspended for inactivity.
- **CI tool maintenance:** Dependabot updates SHA-pinned GitHub Actions weekly. ShellCheck follows the hosted runner; a separate weekly check opens GitHub issues for newer stable Trivy and actionlint releases. Workflow version pins require maintainer review.
- **Gate:** Fedora's `dnf advisory list --security --available --json` is checked after installing all RPMs; any pending security update or query error fails the build. Trivy scans candidate digests on amd64 and arm64. Any scanner error or **fixable HIGH/CRITICAL** CVE blocks `latest`/version tag promotion. Trivy does **not** support Fedora's OS RPM advisory feed; the DNF check covers published updates, not all installed CVEs. **Unfixed** vulnerabilities can remain; false negatives are possible. Failed runs retain the previous published image. The unique candidate tag can remain accessible in a public package.
- **Traceability:** The workflow creates Buildx multi-arch SBOM metadata, two SPDX JSON SBOM artifacts, GitHub provenance and SBOM attestations, and a Cosign keyless signature on the multi-arch image digest. Verify signatures against the repository's *specific workflow identity*, not only the registry address.
- **Rollout:** GHCR does not automatically patch running Podman containers. Pull the new image and recreate each container; retain your named `/work` volume as needed. Production users should pin a verified digest and update it deliberately.
- **GHCR retention:** A daily cleanup deletes versions older than seven days, while preserving `latest` and skipping cleanup if that image is stale or missing. Old release tags, candidate images, digests and GHCR-resident signatures/attestations can become unavailable after cleanup. Retain required artifacts elsewhere before relying on long-lived digest pins. Manual cleanup previews deletions by default.
- **Operational controls:** Protect workflow changes and release tags with appropriate GitHub repository permissions. If `GITHUB_TOKEN` lacks package write permission, grant the repository permission on existing GHCR packages. GitHub Artifact Attestations in private repos require eligible GitHub plans.
- **Reporting:** Use GitHub's private vulnerability reporting feature, when enabled, or contact the maintainer privately. Keep the Fedora and RPM notices intact; see `THIRD_PARTY_NOTICES.md`.
